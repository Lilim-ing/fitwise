# fitwise

内衣尺码和穿着知识助手。尺码由代码按围差计算，知识回答附手册出处，超出知识库范围的问题直接拒答。

```bash
pip install -e ".[dev]"
fitwise size --underbust 78 --bust 90.5
```

```
┌──────────┬───────────┐
│ 推荐尺码 │ 80B       │
│ 围差     │ 12.5 cm   │
│ 姐妹尺码 │ 75C / 85A │
│ 置信度   │ high      │
└──────────┴───────────┘
```

## 尺码计算

围差到罩杯是确定性的算术：每 2.5cm 一档，10cm 是 A，12.5cm 是 B。

LLM 来算这件事，主要风险是算错了还能给出很可信的解释。用户按错误尺码下单，退货成本远高于回答成本。

所以 `sizing.py` 是一个纯函数，8 个测试盯着边界（77→75、78→80、9.9→A、11.3→B）。

## 知识回答

每条回答都能追到 `kb-0xx` 和手册章节：

```
**莫代尔的特点**：莫代尔吸湿透气、手感柔软…
依据：面料手册 §3.1
```

没有出处的句子不进回答。检索只用 18 条短文本，所以用字符 n-gram TF-IDF，不引入 embedding 依赖。

## 拒答

| 场景 | 行为 |
|---|---|
| 医疗问题（肿块、乳腺炎、治疗） | 拒答 + 建议就医 |
| 提示注入（`ignore previous`、`system:`、`扮演`） | 拒答，且不透露触发了哪条规则 |
| 知识库外（天气、竞品、价格） | 拒答 + 给出可问的方向 |
| 检索分数 < 0.12 | 拒答，并显示实际分数 |

拒答话术是固定的，不经过模型自由发挥。一句「我不太确定，但可能是…」比直接说「不知道」更容易误导用户。

## 测试抓到的 bug

姐妹尺码最初写反了：底围减小，罩杯也跟着降了一级。

```python
# 错：75A / 85C
# 对：75C / 85A  ← 底围小了，罩杯要升一级才能装下同样的量
```

这个错误在页面上看不出破绽，两个尺码都合法，只有测试能抓住。

第二个是置信度只检查了杯型上界：围差 11.3cm 贴着 A/B 分界（11.25cm），却报成 `high`；11.2cm 反而正确降为 `medium`。改成同时比较上下两个边界后，分界上方的测量也会提示试两个杯型（回归测试 `test_boundary_above_a_limit_also_lowers_confidence`）。

## 快速开始

```bash
pip install -e ".[dev]"

fitwise size --underbust 78 --bust 90.5     # 算尺码
fitwise ask "75C 的姐妹尺码是什么"           # 问知识
fitwise ask "莫代尔内衣怎么洗"
fitwise ask "帮我算尺码" --underbust 78 --bust 90.5
fitwise search "肩带滑落"                    # 直接看检索结果
fitwise ask "..." --json                     # 结构化输出
```

## 设计取舍

不用 LLM 生成回答。尺码是算术，知识是 18 条短文；加模型会引入幻觉和不可复现两个问题，换不来能力。等知识库到几千条、问题开始需要多跳推理时再考虑。

不用向量检索。18 条文本、问题措辞集中，字符 n-gram 够用。引入 embedding 要多一个模型下载、一个失败点，还要排查召回为什么变了。

拒答做得比较硬。用户问「这个硬块是不是癌」，模型答「可能是乳腺增生，建议观察」，这种回答的伤害是真实的。硬拒答加建议就医是更稳妥的处理。

`parse_size` 单独测，是因为「75C」「75 c」「80AB」这三种输入真实用户都会打出来，边界处理得覆盖到。

## 限制

- 知识库 18 条，覆盖尺码/合身/面料/保养，不覆盖具体商品 SKU
- 尺码表按国标常见档位（65-100 底围），不含欧美尺码换算
- 拒答依赖正则，无法覆盖所有注入变体；生产环境应叠加模型侧防护
- 不做个性化推荐，不接用户历史数据
