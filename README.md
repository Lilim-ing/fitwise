# fitwise

**内衣尺码与穿着知识助手** —— 尺码用算术算，知识带出处答，答不了就说答不了。

```bash
pip install -e ".[dev]"
fitwise size --underbust 78 --bust 90.5
```

```
┌──────────┬───────────┐
│ 推荐尺码 │ 80B       │
│ 围差     │ 12.5 cm   │
│ 姐妹尺码 │ 75C / 85A │
│ 置信度   │ high      │
└──────────┴───────────┘
```

---

## 三条设计原则

### 1. 尺码不许模型算

围差 → 罩杯是确定性的算术：每 2.5cm 一档，10cm 是 A，12.5cm 是 B。

LLM 做这件事的危险不在于"算错"，而在于**算错了还说得很有道理**。用户按错误尺码下单，退货成本远高于回答成本。

所以 `sizing.py` 是一个纯函数，有 8 个测试盯着边界（77→75、78→80、9.9→A、11.3→B）。

### 2. 知识必须带出处

每条回答都能追到 `kb-0xx` 和手册章节：

```
**莫代尔的特点**：莫代尔吸湿透气、手感柔软…
依据：面料手册 §3.1
```

没有出处的句子不进回答。检索只用 18 条短文本，所以用字符 n-gram TF-IDF，不引入 embedding 依赖。

### 3. 默认拒答，而不是硬答

| 场景 | 行为 |
|---|---|
| 医疗问题（肿块、乳腺炎、治疗） | 拒答 + 建议就医 |
| 提示注入（`ignore previous`、`system:`、`扮演`） | 拒答，且**不透露触发了哪条规则** |
| 知识库外（天气、竞品、价格） | 拒答 + 给出可问的方向 |
| 检索分数 < 0.12 | 拒答，并显示实际分数 |

拒答话术是固定的，不经过模型的"自由发挥"——一句"我不太确定，但可能是…"比直接说"不知道"更有害。

## 两个真 bug（测试抓到的）

姐妹尺码最初写反了：底围减小却把罩杯也降了一级。

```python
# 错：75A / 85C
# 对：75C / 85A  ← 底围小了，罩杯要升一级才能装下同样的量
```

这个错误在页面上看起来毫无破绽——两个尺码都合法。只有测试能抓住。

第二个是置信度只检查了杯型上界：围差 11.3cm 明明贴着 A/B 分界（11.25cm），却被报成 `high`；而 11.2cm 反而正确降为 `medium`。改成同时比较上下两个边界后，分界上方的测量也会提示试两个杯型（回归测试 `test_boundary_above_a_limit_also_lowers_confidence`）。

## 快速开始

```bash
pip install -e ".[dev]"

fitwise size --underbust 78 --bust 90.5     # 算尺码
fitwise ask "75C 的姐妹尺码是什么"           # 问知识
fitwise ask "莫代尔内衣怎么洗"
fitwise ask "帮我算尺码" --underbust 78 --bust 90.5
fitwise search "肩带滑落"                    # 直接看检索结果
fitwise ask "..." --json                     # 结构化输出
```

## 设计取舍

**为什么不用 LLM 生成回答？**
尺码是算术，知识是 18 条短文。加一个模型只会引入两个新问题（幻觉、不可复现），换不来任何能力。等知识库到几千条、问题开始需要多跳推理时再考虑。

**为什么不用向量检索？**
18 条文本、问题措辞集中，字符 n-gram 够用。引入 embedding 要多一个模型下载、一个失败点，以及"为什么召回变了"的排查成本。

**为什么拒答这么硬？**
女性用户问"这个硬块是不是癌"，模型答"可能是乳腺增生，建议观察"——这种回答的伤害是真实的。硬拒答 + 建议就医是唯一负责任的处理。

**为什么 `parse_size` 要单独测？**
"75C"、"75 c"、"80AB" 三种输入的边界处理，是真实用户会打出来的东西。

## 边界

- 知识库 18 条，覆盖尺码/合身/面料/保养，不覆盖具体商品 SKU
- 尺码表按国标常见档位（65-100 底围），不含欧美尺码换算
- 拒答依赖正则，无法覆盖所有注入变体；生产环境应叠加模型侧防护
- 不做个性化推荐，不接用户历史数据
